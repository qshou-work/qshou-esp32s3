> 设备：ESP32-S3-COREBOARD V1.4，IP `192.168.65.53`（DHCP，随热点网段漂移），BLE 已连。
> 相机：OV2640 VGA 640×480，JPEG quality 16。手机固定在相机前，画面中手机屏约 196×360 px。
> 工具：`tools/pointer_gain_probe.py`（纯 numpy + PIL，无新增依赖）。

## 0. 本轮要解决的两条物理约束（用户实测反馈）

| 约束 | 失效表现 | 工具侧对策 |
|---|---|---|
| **A. 手机屏无输入即转暗** | `before` 落在暗态、`after` 落在亮态 → 整屏亮度跳变把光标位移彻底淹没，产出一张全错的表 | ① 每次取样前做**净零抖动** `wake()`（+120 再 −120，光标回原位）把屏钉在亮态；② 手势一结束**立刻抢拍** `after`（`SNAP_MARGIN=0.05s`）且**先抓图再读 health**；③ 用「前后帧亮度是否一致」判定这一组能不能用，不一致就重来（`CAPTURE_TRIES=3`） |
| **B. 位移过大会把光标推出可视范围** | `after` 帧里没有光标，差分只剩一个斑块，看起来像「没动」 | ① 每档测量前 `anchor`（−25000 counts 把光标钳到左上角这个可见角）；② 单档位移**自适应钳位**：上限 = 屏幕可见宽 × 0.75；③ 测不到时**重新归零 + 位移减半**重试 |

## 1. 亮屏窗口实测（约束 A 的量化依据）

连续抓帧、期间不发任何手势，画幅均值与过曝占比随时间变化：

| 时刻 | 均值 | 过曝占比 | 状态 |
|---|---|---|---|
| 唤醒前 | 26.8 | 0.0% | 变暗态 |
| 唤醒 +0.5s | 65.4 | 13.0% | 相机 AGC 尚在追赶 |
| 唤醒 +1.0s | 67.8 | 17.1% | **稳定亮态** |
| 唤醒 +1.5s | 67.8 | 17.1% | 稳定亮态 |
| 无输入 +10.8s | 44.0 | 0.0% | 开始变暗 |
| 无输入 +13.7s | 18.9 | 0.0% | 已暗 |

**结论**：① 亮屏窗口只有 **约 10 秒**，所以「等连续 N 帧全局稳定」这类长时间等待只会等来变暗，必须改成「唤醒 → 抢拍 → 判定两帧一致性」；② 唤醒后相机 AGC 要约 **1 秒**才把过曝从 53% 压下来 → `WAKE_SETTLE=1.0`；③ 稳定亮态本身就有 **17% 像素过曝**（那是手机屏自己的白底内容，不是相机被打爆），所以过曝门限必须按这个基线抬到 0.35，否则每一帧都会被误判。

**净零抖动的正确性验证**（三次独立试验）：

| 试验 | 亮度 Δ | 亮度一致 | 残留差分最大面积 |
|---|---|---|---|
| 净零抖动 ×1 | 44.56 | 否（恰好赶上变暗） | 64746 px（假） |
| 净零抖动 ×2 | 0.02 | 是 | **20 px** |
| 净零抖动 ×3 | 0.04 | 是 | **21 px** |
| 对照：真实 +400 counts 位移 | 0.96 | 是 | **5452 px** |

→ 净零抖动的残留只有真实位移的 **1/250**（相当于光标自身重叠残差），可安全用于测量前唤醒。

## 2. 增益实测数据

### 2.1 X 轴，`step_ms=90`（v = 0.37 counts/ms）

| counts 请求 | 实际下发 | 实测位移 | cap_px/count | 丢帧 | 亮度Δ |
|---|---|---|---|---|---|
| 150 | 150 | 42.2 px | 0.2816 | 0 | 0.03 |
| 300 | 300 | 83.9 px | 0.2798 | 0 | 0.02 |
| 600 | **523**（安全钳位） | 145.2 px | 0.2777 | 0 | 0.03 |

**拟合：`gain = 0.27843 cap_px/count`，R² = 0.999982，逐点离散度 1.4%，最大残差 0.48 px。**

### 2.2 Y 轴，`step_ms=90`

| counts | 实测位移 | cap_px/count |
|---|---|---|
| 150 | 33.6 px | 0.2241 |
| 300 | 67.8 px | 0.2260 |
| 600 | 142.6 px | 0.2377 |

**拟合：`gain = 0.23483 cap_px/count`，R² = 0.999514，离散度 6.1%，最大残差 2.66 px。**

### 2.3 X 轴，`step_ms=15`（v = 0.83 counts/ms，比 2.1 快 2.25 倍）

| counts 请求 | 实际下发 | 实测位移 | cap_px/count |
|---|---|---|---|
| 150 | 150 | 61.7 px | 0.4115 |
| 300 | 300 | 135.4 px | 0.4513 |
| 600 | **340**（安全钳位） | 136.7 px | 0.4022 |

**拟合：`gain = 0.42249 cap_px/count`，R² = 0.99693，离散度 12.2%，最大残差 8.66 px。**

## 3. 结论

1. **固定节奏下增益是线性的**：X 轴在 150→523 counts（3.5 倍）范围内逐点增益只差 1.4%，R²≈1。所以在**固定 step_ms** 的前提下，可以用单一常量描述。
2. 🔴 **增益强依赖速度（指针加速度确实存在）**：同样 150/300 counts、同样距离，只把 `step_ms` 从 90 改成 15（速度 ×2.25），增益从 **0.278 → 0.422（+52%）**。
   → 「counts ↔ 屏幕像素」**不是一个常量**。控制策略要么固定节奏（推荐先用这条），要么做速度分段增益，或者闭环校正（移动后量落点再补）。
3. **两轴增益不同**：同速下 X=0.2784、Y=0.2348（差 18%）。这与相机透视（手机在画面里是斜的）和安卓两轴缩放都可能有关 → 必须分轴标定，且**标定与相机/手机的安装绑定**。
4. **安全钳位按设计工作**：600 counts 在两轴分别被收敛到 523 / 340，光标始终留在画面内，该点仍有效（未被撞边污染）。
5. **诊断门按设计工作**：变暗轮次（Δ=63.2 / 82.3 / 19.5 / 32.9）被自动识别并**排除出收敛依据**，避免把「屏幕被手势唤醒」误判成「光标还在大幅移动」（曾出现 14003 px 的假斑块）。

## 4. 复现命令

```bash
IP=192.168.65.53
P=<python>

# 自证（无需设备）
$P tools/pointer_gain_probe.py selfcheck
$P tools/pointer_gain_probe.py simulate --counts 50,100,200,400,800

# 真机：单点探针（含预检 + 前后帧落盘到 .tmp/pgprobe/）
$P tools/pointer_gain_probe.py probe --ip $IP --counts 400 --axis x

# 真机：分档扫描（自动归零 + 安全钳位 + 闪烁重试）
$P tools/pointer_gain_probe.py scan --ip $IP --counts 150,300,600 --axis x --json out.json
$P tools/pointer_gain_probe.py scan --ip $IP --counts 150,300,600 --axis y --json out.json
$P tools/pointer_gain_probe.py scan --ip $IP --counts 150,300,600 --axis x --step-ms 15 --json out.json

# 不需要相机的权威交叉校验（安卓「开发者选项 → 指针位置」）
$P tools/pointer_gain_probe.py manual --ip $IP --counts 200,400,800
```

## 5. 已知限制 / 待办

- 以上都是**相机像素域**的增益。换算到**屏幕像素**还需第二把尺子（相机像素 ↔ 屏幕像素的单应 `H`），当前只能用相机透视近似（屏宽 196 cap px ↔ 1080 scr px ⇒ ≈5.5 scr px/cap px），不够准。
- 增益与相机/手机安装强绑定：位置一挪即失效，结果需带 `device_id` + 时间戳。
- 观测到一例**撕裂帧**（画面上下两半错位）。该帧被「小而紧凑 + 面积相近 + 落在屏内」的光斑判据拦下、未产出错误数据，但成因未定位（连续 10 帧完整性检测 10/10 通过、均带 EOI，故非传输截断）。暂按偶发处理。
- 屏幕亮度仍会漂移（亮态也会 ±8 灰阶跳动），故「亮度一致性门限」放宽到 15 灰阶；该门限可用 `--pair-tol` 调。
